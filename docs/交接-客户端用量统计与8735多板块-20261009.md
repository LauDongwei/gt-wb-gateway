# 交接：把「WorkBuddy 客户端自己烧的 token」变成可见（2026-10-09）

> 配套阅读：本文只讲**本次新增的客户端用量统计**。网关的整体架构、投影层、
> 三根因定位等历史内容，见同目录 `全史交接-网关一个月-20260911至20261009.md`。

## 0. 三十秒看懂

**改了什么事**：以前看板只统计「经网关转发的 token」（Codex / Claude Code / curl）。
WorkBuddy 桌面端**自己**调用同一批模型时并不经过网关，这部分消耗完全不可见，
于是「某个模型一天一共用了多少」永远算不全。

现在：**8735 状态看板改成三个板块 Tab**，新增「模型用量（网关 + 客户端合计）」
与「按日明细（可查任意日期）」。

**数据从哪来**：不在官方接口，在**本机**——
`~/.workbuddy/traces/<workerPid>/trace_*.json`。

**动了哪些文件**：

| 文件 | 变化 |
|---|---|
| `deploy/wb_trace_stats.py` | **新增**，只读聚合器 |
| `deploy/status_server.py` | 改：三板块 Tab + `GET /api/day` + KPI 补 `total_tokens` |
| 计划任务 `gt-dashboard-8735` | **新增**，让 8735 真正常驻（原靠 serve-loop 顺风车，有缺陷） |

## 1. 先走死的一条路：官方接口（别再试）

用户的第一反应是「去官方接口拉」。**实测走不通**，把结论记下来免得重走：

| 尝试 | 结果 |
|---|---|
| 猜 5 个用量明细接口（`get-user-usage-detail` / `list-user-usage` / `get-user-usage-record` / `get-user-consume-detail` / `get-daily-usage`） | **全 404** |
| 客户端 `app.asar` 里 26 个 `/spapi/*` 路径 | **全是企业知识库 / 团队 / 权限**，与 token 无关 |
| 唯一可用的 `/v2/billing/meter/get-user-resource` | 返回 **credits（积分）**，不是 token；且只有**账号级周期汇总**（62 个套餐），**无按日、无按模型粒度** |

**教训**：接口**不要靠猜**。猜出来的路径回来全是 404，白白浪费一轮。
要看真数据，去**反查客户端源码 / 找它自己的落盘文件**。

## 2. 真数据源：`~/.workbuddy/traces/`

客户端把**每一次模型调用**都写成了一个 trace 文件：

```
C:\Users\Administrator\.workbuddy\traces\<workerPid>\trace_<hash>.json
```

### 2.1 文件结构

```jsonc
{
  "trace": {
    "traceId": "trace_c24fe7...",
    "name": "Agent workflow",
    "workerPid": 18672,
    "startedAt": "2026-09-19T08:49:35.228Z",   // ← 取日期 / 小时
    "endedAt":   "2026-09-19T09:07:50.750Z",
    "totalTokens": 0                            // ⚠ 实测恒为 0，别信这个字段
  },
  "spans": [
    { "type": "generation", "toolOutput": "<一段 JSON 字符串>", ... },
    { "type": "function",   "name": "Read", ... },
    { "type": "custom",     "name": "mcp_tools", ... }
  ]
}
```

### 2.2 关键点（三个坑）

1. **只认 `type == "generation"` 的 span**，其余（`function` / `custom` / `agent`）不是模型调用。
2. **`toolOutput` 是字符串，不是对象** —— 要 `json.loads` 二次解析。解析后是标准 OpenAI 响应体：
   ```jsonc
   [{
     "id": "...", "model": "deepseek-v4.1-flash",
     "usage": {
       "prompt_tokens": 86676,
       "completion_tokens": 450,
       "total_tokens": 87126,
       "prompt_tokens_details":     { "cached_tokens": 83840 },
       "completion_tokens_details": { "reasoning_tokens": 0 }
     }
   }]
   ```
3. **顶层 `trace.totalTokens` 是 0** —— 别图省事用它，得自己从 span 里累加。

### 2.3 实测规模（2026-10-09）

```
1221 个 trace 文件 · 5868 次调用 · total 8.96 亿 token
覆盖 2026-09-17 → 2026-10-09（11 个活跃日）
09-26 ~ 10-07 无数据 —— 国庆假期没办公，正常，不是丢了
```

按模型：

| 模型 | 调用数 | total tokens | 缓存率 |
|---|---:|---:|---:|
| deepseek-v4.1-flash | 4983 | 803,134,343 | 97.5% |
| glm-5.3-flash | 612 | 67,884,985 | 96.3% |
| space-bunny | 137 | 15,726,996 | 97.4% |
| hy3 | 136 | 8,992,880 | **46.1%** ← 异常值，待查 |

## 3. 两套账不重复，可以相加

**这是全部逻辑的地基，务必先理解**：

| 账 | 来源文件 | 记什么 | 谁产生 |
|---|---|---|---|
| **网关账** | `gt-wb-gateway/usage-stats.jsonl` | 经本网关转发的调用 | Codex / Claude Code / curl |
| **客户端账** | `~/.workbuddy/traces/**` | WorkBuddy 桌面端自己的调用 | WorkBuddy 客户端本体 |

两条链路的 `prompt / completion / total / cached / reasoning` **同名字段同义**，
所以**直接相加 = 某模型的整体用量**。这正是用户要的答案。

> ⚠️ 别把「8731 看板的 `quota.used`」也算进来 —— 那是上游的 **credits** 单位、
> 账号级周期容量，**含官方客户端 + 其他设备 + 其他上游**在内的一切消耗，与 token 不是同一回事。

## 4. 实现

### 4.1 新增 `deploy/wb_trace_stats.py`（聚合器）

```python
from wb_trace_stats import WbTraceIndex

idx = WbTraceIndex()                  # 默认 ~/.workbuddy/traces，可用 GTWB_TRACES_DIR 覆盖
idx.day("2026-10-08")                 # 整日：合计 + 按模型拆分 + 按小时
idx.daily(7)                          # 最近 7 天按日合计
idx.models(days=7)                    # 最近 7 天按模型合计
idx.available_days()                  # 有数据的日期列表（给前端选择器）
idx.summary()                         # 全量概览
```

**设计要点（照抄，别省）**：
- **不抛异常**：任何单文件解析失败只计数跳过 —— 看板不能因一个坏文件挂掉。
- **文件级 mtime 缓存**：键 = `(路径, mtime, size)`；trace 落盘后不再改写，
  所以重复扫描近乎零成本。实测 **首扫 6.6s → 复扫 0.06s（110×）**。
- **口径与网关一致**：五字段同名同义，可直接相加。

### 4.2 改 `deploy/status_server.py`（看板）

**后端**：
- `build_data()`：`kpi` 补 `total_tokens`；新增 `modelRows`（网关/客户端/合计 合并视图）；
  新增 `wb` 块（客户端侧今日 + 近 7 天 + summary）。
- **新增 `build_day(date)`**：返回 `gatewayTotal` / `clientTotal` / `combinedTotal` /
  `modelRows` / `gwHours` / `wbHours`。
- **新增路由 `GET /api/day?date=YYYY-MM-DD`**，日期用
  `re.fullmatch(r"\d{4}-\d{2}-\d{2}")` 校验，非法返 **400**。
- **后台预热线程**：首次扫 traces 6~8s，放 `threading.Thread(daemon=True)` 里先跑，
  避免第一个 `/api/data` 阻塞（缓存命中后单次仅几十毫秒）。

**前端**：单页改**三板块 Tab**：
1. **总览** —— 沿用原有 KPI / 按小时 / 客户端来源 / 异常 / 最近请求。
2. **模型用量** —— `modelRows` 表 + 双色占比条（**蓝=网关 · 紫=客户端**）
   + 「WorkBuddy 客户端自身消耗」卡。
3. **按日明细** —— 日期选择器 + 快捷日按钮 → 调 `/api/day` → 整日汇总卡 +
   按模型拆分 + 按小时堆叠柱。

### 4.3 8735 自启改为独立计划任务（★原方案有缺陷）

**原方案**：`serve-loop.bat` 在 `:loop` 顶部探 8735，down 就 `start` 拉起。
看着没问题，**实际有缺陷**：

```
:loop
 探 8735 → down 就 start dashboard
 探 8787 → 健康就 exit /b 0        ← 网关健康时整轮在此退出
 python -m gtwb                     ← 否则卡在这行前台运行（阻塞）
```

→ 网关一直健康时，serve-loop **整轮就退出，永远不回到循环顶部再检查 8735**。
所以 8735 只在「网关重启时」被顺带拉起，网关不掉它就永远不起来。

**修法**：照抄 8731 的模式，建独立计划任务：

```
任务名   : gt-dashboard-8735
Execute  : D:\workbuddy\研究院\gt-wb-gateway\.venv\Scripts\pythonw.exe
Arguments: "D:\workbuddy\研究院\gt-wb-gateway\deploy\status_server.py" --port 8735
WorkingDir: D:\workbuddy\研究院\gt-wb-gateway
Trigger  : AtLogOn · S4U · MultipleInstances=IgnoreNew · RestartCount=999
```

`serve-loop.bat` 里的 8735 段**保留但不依赖**（幂等，健康就跳过，属双保险）。

## 5. 踩过的坑

### 5.1 ★ 从 Agent / 脚本环境拉起的进程**必被回收**（又踩一次）

| 试过的方式 | 现象 |
|---|---|
| `nohup python ... &` | 端口 1 秒内报就绪 → 命令结束 → 进程消失，**无报错** |
| `os.startfile(...)` 派生 bat | 同上 |
| `subprocess` / `cmd /c start` | 同上（`cmd /c start` 直接被安全策略拦） |
| `wscript.exe` / `cscript.exe` | 被安全策略拦（LOLBin） |

**根因**：发起进程在 Job Object 里，命令结束时清理整棵子树。
**唯一可靠路径**：`Start-ScheduledTask -TaskName gt-dashboard-8735`（S4U，在 session 0）。

### 5.2 `0x800710E0` 是「被拒」，不是故障

serve-loop 的 `MultipleInstances=IgnoreNew` 会让手动 `Start-ScheduledTask` 在
已有实例运行时返回 `0x800710E0`（The operator or administrator has refused the request）。
**看到它说明服务健在**，别当故障排查。

### 5.3 探测一律带 `--noproxy "*"`

本机 shell 导出 `HTTP_PROXY/HTTPS_PROXY`，`urllib` / `curl` 探 `127.0.0.1` 会被劫持到代理
→ 误判「服务已死」。**任何健康探测都必须绕代理**。

### 5.4 后台任务里 `TaskOutput` 别轮询

`run_in_background` 起的实例端口就绪很快，但**会话结束仍会被回收**。
它的价值只是「临时验证」，**要常驻必须走计划任务**。

## 8. 怎么同步到你那台

**别复制文件夹**（会因 CRLF / 环境差异出问题），**拉同一个 git 提交**：

```bash
cd <你的 gt-wb-gateway-oss 目录>

```

然后按需重建 8735 的独立计划任务（见 §4.3）。
注意：**客户端 traces 目录是每台机器各自的**，深圳机上的 traces 是它自己那份，
两台的数据**不需要也不应该合并**（各自统计各自的客户端消耗）。
