## 0. 三十秒看懂这个网关

**它是什么**：把 WorkBuddy / CodeBuddy 桌面端订阅，转成本机可用的
**OpenAI 兼容（`/v1/chat/completions`、`/v1/responses`）+ Anthropic 兼容（`/v1/messages`）** API，
供 Codex CLI、Claude Code、CC Switch、Cherry Studio 等复用。

**端口布局**：

| 端口 | 服务 | 说明 |
|---|---|---|
| **8787** | 网关 API | 主服务；`/` 返回 404 属正常 |
| 8735 | 状态看板 | **三板块 Tab**：总览 / **模型用量（网关+客户端合计）** / **按日明细** |
| 8731 | 用量看板 | **独立项目** `wb-usage-widget`，直连上游取配额 |
| 3100 | WebDAV | 文件服务 |

**核心链路**：

```
Codex CLI / Claude Code  ──HTTP──▶  :8787 网关  ──▶  copilot.tencent.com
   （不含账号）                    账号唯一出口         （WorkBuddy 订阅后端）
```

**★ 最关键的一层是「投影层」（`responses_projection.py`）**：Codex 会把完整历史、
全套工具 schema、运行时提示一股脑发过来（实测峰值 **1.94M 字符**），而后端有接收上限。
网关必须在不丢「能让 agent 继续干活的信息」的前提下，把请求压到后端能吃的规模。

**工程位置**：`D:\workbuddy\研究院\gt-wb-gateway\`
**公开仓库**：`https://github.com/LauDongwei/gt-wb-gateway`（OSS 副本在 `..\gt-wb-gateway-oss\`）

## 2. 阶段详解

> 每节统一按 **现象 → 根因 → 修法 → 验收** 组织。**根因部分是最值钱的**，因为那是排查思路。

### 2.1 【09-15~17】namespace 工具提升 —— 让 computer/browser use 能用

**现象**：Codex 的 computer use / browser use 在别家中转可用，唯独走本网关不行。

**排查弯路（重要）**：日志显示 `tools 12→12`，**看起来没丢**。但实际上
`_convert_tools_for_chat` 的静默丢弃发生在 projection 计数**之前** ——
**「没变」不等于「没丢」**。

**实锤**：加诊断日志，让网关每请求落「声明工具清单 + drop 告警」，拿到：
Codex 每请求声明 23 个工具，其中 **11 个 `type:namespace`** 全被静默丢弃。

```
{type: namespace, name: mcp__cua_repl, tools: [...]}   ← Chat 协议不认这个容器
```

**根因**：Codex 0.117+ 用 namespace 容器打包 MCP 工具；Chat 协议只认扁平 function。

**修法（5 处）**：① 子工具**提升**为顶层 function（重名跳过 + 日志）；
② `responses_request_to_chat` 返回 `(chat_tools, bare_to_ns)` 映射；
③ 回传时在 `_fc_item` **还原** `namespace` 字段；④ server 传映射；⑤
`_project_tools` **保留工具 description（截 500 字符）** —— 原来全剥掉，模型不知道工具用途自然不调用。

**可迁移教训**：
> 容器型工具（namespace）= **提升为顶层 function + 回传还原容器字段**，两步缺一不可。
> 排查「静默丢弃」类问题时，**先让代码把丢弃打出来，拿实锤再动手**。

### 2.2 【09-17】透明模式上线 —— 思路转折点

**背景**：用户总感觉 Mac 上 Codex 各模型效果差。对标 `github.com/Wei-Shaw/sub2api` 后得出：

**对标结论**：sub2api 是「订阅配额透明代理」，核心优点是**不改写对话内容**；
我们的核心短板恰恰是 **激进投影丢 88% 上下文**（日志实证 `76465 → 9272` chars）。

**修法**：引入 `TRANSPARENT_CHAR_LIMIT` ——
阈值内**原样透传**（全量指令 / 历史 / 完整 schema，只加语言规则），超限才压缩。

**可迁移教训**：
> **代理改写内容是有代价的。** 多租户 / 计费 / 账号池这类能力对单用户单上游场景无意义，
> 但「保真度」（不改写）和「可靠性」（重试、上限、透传）必须搬。

### 2.3 【09-19】三根因定位 —— 这次是分水岭

**用户提问**：（Codex function call 不好用）「是协议问题还是公司电脑配置问题？」

**答案：都不是，是网关自己把请求压坏了。**

#### 根因 1：投影层「二元开关」，一把砍掉 99%

旧实现 >120k 字符就压到 ~6k。用真实抓包（47,053 字符）实测：

| 项目 | 原始 | 旧投影后 |
|---|---|---|
| instructions | 21,026 字符 | **173 字符** |
| 工具 description | 9 个非空 | **全部清空** |
| 仓库指令 / AGENTS.md | 有 | 丢失 |

#### 根因 2：身份声明句触发上游安全策略 `11128`

上游返回 `{"code":11128,"msg":"Illegal API invocation from an unapproved channel"}`。
**逐项减法定位**（这是排查范式，值得学）：

| 减法动作 | 结果 |
|---|---|
| 仅删「身份声明句」（1 处） | ✅ 200 |
| 仅删「Codex 品牌词」（13 处） | ✅ 200 |
| 删掉全部 harness 段 | ✅ 200 |
| **保留身份句、只清空工具描述** | ❌ 400 / 11128 |

→ **唯一触发点就是身份声明句**（`You are a coding agent running in the Codex CLI` 之类），
与指令正文、工具描述、提示词长度**都无关**。

**修法**：不是整段压缩，而是**只中和身份、逐字保留行为指令**
（`neutralize_identity_text`）。

#### 根因 3：关键字段被静默丢弃

| 字段 | 后果 |
|---|---|
| `reasoning.effort`（嵌套结构） | 推理强度没传上去 |
| `prompt_cache_key` | 上游缓存失效，每轮全量重算 |
| `parallel_tool_calls` | 模型不敢并行调工具，轮数翻倍 |
| 模型名不兜底 | 客户端发 `gpt-5.6-luna` 这类不存在的名字 → 400 → **agent 直接崩** |

**验收**：

| 档位 | 载荷 | 结果 |
|---|---|---|
| none（完全不脱敏） | 47,053 字符 | ❌ 400 / 11128 |
| **lossless（身份中和）** | **47,140 字符**（保 99.8%） | ✅ **200 首轮直达** |
| compact（降级） | 6,811 字符 | ✅ 200（现在只是兜底） |

长上下文 A/B（693,834 字符真实会话）：**保留率 2.2% → 53.3%**。
旧投影下模型明确回答「我无法回答第二个问题……我不能凭空编造这两个数字」——
**这就是之前 agent 失忆、乱调工具的直接机制。**

**可迁移教训**：
> **旁路功能「开了却没效果」比崩溃更难发现。** 本次抓到诊断抓包长期静默失效，
> 根因是 `server.py` 漏 `import os`，异常被 `except: pass` 吞掉。
> 现在同类问题会留一行 `⚠ 抓包失败`。

### 2.4 【09-19】客户端身份上报 —— 让用量明细的「客户端」列不再为空

**现象**：官方客户端产生的记录显示 `WorkBuddy`，经网关的记录该列**为空**。

**根因**（不是出错，是没发头）：网关早期只发 `Authorization` + `X-Product: SaaS`，
**漏了 IDE 身份三件套**。证据取自本机安装包（非推测）：
桌面端 `app.asar` 向 agent-cli 注入 `CLIENT_INFO_*` 环境变量。

**修法**：`upstream.py::chat_headers()` 按官方形状补齐：

| 头 | 改前 | 改后 |
|---|---|---|
| `X-IDE-Type` | 未发 | `WorkBuddy` |
| `X-IDE-Name` | 未发 | `WorkBuddy` |
| `X-IDE-Version` | 未发 | 自动探测本机安装版本 |
| `User-Agent` | `CLI/2.63.2 CodeBuddy/...` | `WorkBuddy/<ver> ... CLI/<ver>` |

**边界（必须说清）**：它让归因**准确**，**不改变**「用第三方客户端消耗订阅额度」这件事的性质 ——
那取决于订阅条款，与发不发这组头无关。

### 2.5 【09-19 深夜】并行工具 + 图片 → 上游 400 `11148`

**现象**：Mac 真实 agent 会话中，唯一一次失败直接打断任务：
```
◀ 200 | finish=tool_calls | tools=['view_image', 'view_image']
✗ HTTP 400 | {"code":11148,"msg":"tool calls and tool results do not match"}
```

**根因**：工具输出里的图片被摘出后**立刻**插一条 user 消息承载。
一轮有多个工具调用时结构变成：

```
assistant(tool_calls=[A, B])
tool(A)
user(图片)      ← 隔断！
tool(B)
user(图片)
```

Chat 协议要求 `assistant.tool_calls` 之后**连续**跟上同等数量的 tool 消息。B 被 user 隔开 → 配对失败。

**修复**：新增 `pending_tool_results` 缓冲 + `_flush_tool_results()` ——
图片 user 消息**推迟到整组 tool 结果之后**统一发出。

**离线复现（确定性，这是好实践）**：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 单个 `view_image` | ✓ | ✓ |
| **两个并行 `view_image`** | **✗ 破坏** | ✓ |
| 两个并行 `exec_command`（纯文本） | ✓ | ✓ |
| 两个并行，仅一个带图 | **✗ 破坏** | ✓ |

与日志完全吻合 —— 差别只在有无图片消息插入。

**可迁移教训**：
> **离线复现脚本（`repro_xxx.py`）是把「偶发」变成「确定性」的利器。**
> 有了它，修复前后对照一目了然，回归断言也有了依据。

### 2.6 【09-19 深夜】网关侧联网搜索 —— 用户不接受「Mac 没搜索」

**排查结论**：上游（copilot 后端）**没有任何原生搜索能力** ——
六种参数形态（`enable_search` / `web_search_options` / Codex 托管 `web_search` …）
全部被静默忽略，模型明确回答「无法联网」。

**唯一可行方案：网关自己执行搜索，把结果回灌给模型。**

**搜索源选型（全部实测）**：

| 候选 | 结果 |
|---|---|
| DuckDuckGo html/lite | ❌ 反爬，返回首页 |
| Bing HTML / RSS | ❌ 出口 IP 被判滥用，返回噪声（标题对、内容全错） |
| SearXNG 公共实例 | ❌ 拒绝或无 JSON |
| **Google News RSS** | ✅ 直连即通，55 条中 52 条真实相关 |
| **cn.bing / 360 / Wikipedia** | ✅ 可用，质量泛化但真实 |
| **GitHub / StackExchange API** | ✅ 结构化，开发者查询质量高 |

**实现**：内部工具循环 —— 模型调 `web_search` → 网关并发跑多引擎 → 结果回灌 → 重开上游续跑。
客户端只看到最终答案（中间轮不发终止事件）。

**三条防线**：
1. **多轮累积**（`msgs_acc` 逐轮叠加）——早期每轮从原始 body 重建，
   搜索结果被丢、模型「失忆」反复重搜，已修；
2. **重复 query 去重缓存** + 无进展轮短路；
3. **轮次上限**（默认 3）→ 跑「收尾轮」强制作答，避免「我再查证一下」当终稿。

**后续质量修复**：模型在第 2、3 轮把上一轮 query **原样重发** →
两个会话拖到 82.5s / 72.1s。新增 `_all_queries_cached()` + 循环短路：
某轮调用**全部命中缓存**即判「无进展轮」，直接进收尾轮。

### 2.7 【09-21】模型清单超发 9 个「幽灵模型」

**现象**：下游（Mac）反馈「有一部分模型无法使用」。`/v1/models` 报 **31 个**，
逐个探测有 **9 个 400**：
```
{"code":11102,"msg":"model [glm-4.6] service info not found"}
```

**根因**：上游 `GET /console/enterprises/personal/models`（**注意 GET，POST 会 404**）
返回**三层数据**，只有第一层是给外部客户端用的：

| # | 位置 | 是什么 | 能对外吗 |
|---|---|---|---|
| ① | `data.agents[]` 里 tags 含 **`cli`+`default`** 的那个 | 账号真实可用的 CLI 模型（实测 16 个全部 200） | ✅ **唯一权威** |
| ② | 其余 agent（`sub-agent` 标签） | **内部子任务**用的轻量模型（就是 `lite`） | ❌ 外部调必 400 |
| ③ | `data.models[]` 账号级目录 | 含已下线/未开通条目 | ⚠️ **混合**：14 个里 6 个能用、8 个 11102 |

旧 `_extract_model_ids()` 把 ①②③ **全并** → 31 个里混进 9 个幽灵。
**客户端照着清单选就 400，整条 agent 当场断。**

**修法两层**：
1. **清单**：只取 ①，取到就 `return`（顺带 push `default` 别名）；
2. **守卫 `model_guard`（默认开）**：`resolve_model()` **默认查清单**，
   清单外的名字**不发上游**，直接换 `model_fallback`。

**为什么守卫必须默认开**：**客户端会缓存旧清单**，改完服务端它照样选到幽灵 → 还是 400。
守卫是第二层保险。边界：`auto` 永远放行、aliases 优先、**清单为空时放行**。

**验收**：`glm-4.6` / `lite` / `glm-5.0` 三个幽灵 **400 → 200**；
`/v1/models` **31 → 17 个**。

**可迁移教训**：
> 「客户端会缓存服务端清单」是一条容易被忽略的耦合 —— **改了服务端不等于生效**。
> 服务端要有一层「不认的名字就拦下」的守卫。

### 2.8 【09-21】用量记账：账本必须等于「客户端所见」

**现象**：Mac 上 Codex 显示的 token 和看板统计的不一样。

**根因（两条，别混为一谈）**：
1. **网关自己记错了** —— `_responses_stream` 里对**每一轮**上游 SSE 都写 `stat.usage`，
   **后写覆盖前写**；而给客户端的 usage 是**跨轮累加**值。
   → **长上下文 + 多轮搜索时看板能比客户端少记 4~5 倍。**
   **修法**：收尾时用累加值覆盖回去，**且 `stat.tokens` 必须同步改**
   （日志行的 `tokens=` 读的是它，只改 usage 会产生新的不一致）。

2. **口径本来就不同（不是 bug）**：
   - 网关/看板 = **经本网关转发**的 token；
   - **8731 的 `quota.used`** = 上游「**账号级周期容量**」消耗，
     **含官方客户端、其他设备的一切消耗** —— 与 token 不是同一单位。

**★ 账单审核的固定起手式（别一上来就算总数）**：
```bash
# ① 先证明「那台机器到底走没走本网关」——看 client_ip，别猜
python -m gtwb --diag
# ② 再看记账链路是否还活着（发最小请求，前后比文件行数）
# ③ 最后才核对总量
```
**判断「网关是不是根本没收到请求」的硬证据**：
`gtwb.log` 与 `usage-stats.jsonl` **最后一条的时间戳**。
两者都比「现在」旧很多 = 那段流量**没走本机**，**不是统计漏了**。
**反例对照：`/health` 正常 ≠ 有流量。**

### 2.9 【09-24】客户端升级把 token 加密 → 全线 401（★一类独立故障源）

**现象**：WorkBuddy 更新后，**网关与 8731 看板同时全挂**（401），
报错 `Header value must be str or bytes, not <class 'dict'>`。

**根因**：客户端的 auth 文件里 token 变成了 `{"$wbEncrypted": ...}` 结构，
网关把它当字符串用 → 拼头失败。

**★ 更凶的连锁反应**：这个 401 被健康状态机判成 `session_dead`，
**持久禁用账号** —— 结果**修好 token 仍然是 503**，看起来像「没修好」。

**修法（3 处）**：
1. **新增 `gtwb/wbtoken.py`** —— 动态加载 skill 的解密器
   （`~/.workbuddy/skills/wb-encrypted-token-decrypt/scripts/wb_decrypt.py`）。
   **密钥/算法只留 skill 一处**，客户端下次换 key 只改 skill。
2. `gtwb/auth.py`：三个字段各套一层 unwrap；
   `_write_back()` **遇到加密格式直接跳过**（网关只解密不重新加密）。
3. `wb-usage-widget/gateway_stats.py`（**独立项目**）：加 `_unwrap_wb()`。

**恢复入口**：`python -m gtwb --enable-account UID|all`（解除持久禁用）。
**⚠ 必须先停服务** —— 状态是进程内缓存。

**可迁移教训（三条，都很硬）**：
> ① **「客户端升级」是一类独立的故障源**，症状是「服务活着但全 401」。
> ② **同一个根因会打穿多个项目** —— 网关 + 8731 读同一个 auth 文件。
>    修这类问题要**先列出所有读该数据的入口**，只修一个会留下「一半好一半坏」。
> ③ **状态机会把「网关自己造成的 401」判成账号级失效且持久化** ——
>    修好根因后必须**显式解除**，否则一直 503。

### 2.10 【10-09】缓存断崖 + 上下文容量（★这两件是同一件事）

#### 症状

用户在看板上发现「缓存越来越少」。按日聚合 `usage-stats.jsonl`：

| 日期 | 请求数 | prompt 合计 | cached 合计 | 命中率 |
|---|---|---|---|---|
| 09-19 | 356 | 34,379,644 | 32,485,376 | **94.5%** |
| 09-20 | 263 | 30,627,667 | 29,646,336 | **96.8%** |
| 10-08 | 1155 | 178,606,586 | 129,185,166 | 72.3% |
| **10-09** | **59** | **10,045,601** | **662,272** | **6.6%** ← 断崖 |

**逐条模式更露骨**：每条 `prompt` ≈ 176k–182k，而 `cached_tokens` **恒定只有 12,032**
→ 命中率卡死。**12,032 = 固定 system 前缀，历史部分 0 命中。**

#### 根因：一行常量

```python
TRANSPARENT_CHAR_LIMIT = 600_000   # 按字符数硬编码，跟模型能力完全脱钩
```

```
会话字符 > 600k
  → 投影落 elastic 档（滑窗 + 历史重摘要）
  → 每轮投影出的 messages 序列都不一样
  → 上游 KV 前缀缓存整段失效
```

对 **1M token 的模型**（`deepseek-v4.1-flash` 就是）而言，
60 万字符 ≈ 18 万 token ≈ **容量的 18%** —— 会话稍长就永远在弹性档里。**必然，不是偶发。**

#### ★★ 决定性发现：上游早就把上下文长度给我们了，是我们自己扔了

`data.models[]` 每条都带 `maxInputTokens` / `maxOutputTokens` / `maxAllowedSize` /
`contextWindow{defaultLength, supportedLengths[]}` / `credits` / `vendor` / 模态开关。
改前 `grep -rn "contextWindow\|maxInputTokens" gtwb/*.py` = **零命中**。

**实测各模型真实容量**：

| 模型 | maxInputTokens | maxOutputTokens |
|---|---|---|
| deepseek-v4.1-flash / deepseek-v4-pro | **1,000,000** | 128,000 |
| glm-5.3 / glm-5.3-flash / glm-5.2 | **1,000,000** | 64k / 131k / 64k |
| kimi-k3-1 / kimi-k2.8-preview | **1,000,000** | 32k / 64k |
| space-bunny | **1,000,000** | 128,000 |
| hy4-preview | 960,000 | 64,000 |
| minimax-m3 | 512,000 | 64,000 |
| kimi-k2.7 / kimi-k2.6 / auto | 256,000 | 32,000 |
| glm-5.1 / glm-5v-turbo | 200,000 | 48k / 64k |
| hy3 / hy3-x | 192,000 | 64,000 |

#### 修法（三步）

| # | 文件 | 做了什么 |
|---|---|---|
| 1 | `gtwb/upstream.py` | `CATALOG_FIELDS` + `_extract_model_catalog()` + `fetch_model_catalog()`。**口径与 `_extract_model_ids()` 严格一致** |
| 2 | `gtwb/server.py` | `_MODEL_CACHE` 加 `"catalog"` 键（与 ids **共用同一份 TTL**）；`model_catalog()` / `model_max_input()` / `model_max_output()`；`/v1/models` 加 `context_length` + `max_output_tokens` |
| 3 | `gtwb/responses_projection.py` | `transparent_char_limit_for()`；投影签名加 `max_input_tokens` |

```python
CHARS_PER_TOKEN = 3        # 中英混排经验值
CAPACITY_SAFE_RATIO = 0.7  # 留 30% 给工具 schema、语言规则、输出

def transparent_char_limit_for(max_input_tokens: int | None) -> int:
    if not max_input_tokens or max_input_tokens <= 0:
        return TRANSPARENT_CHAR_LIMIT          # 查不到 → 回落旧常量
    scaled = int(max_input_tokens * CHARS_PER_TOKEN * CAPACITY_SAFE_RATIO)
    return max(TRANSPARENT_CHAR_LIMIT, scaled)
```

**效果对照（真实规模 body）**：
```
旧：写死常量        阈值=  600,000   elastic      1,837,823 字符 → 裁到 346,471
新：deepseek (1M)   阈值=2,100,000   transparent  1,838,047 字符 → 原样透传 ✅
新：hy3 (192k)      阈值=  600,000   elastic      1,838,047 字符 → 裁到 346,695
```

#### 为什么网关这层压缩不能砍（用户问过）

**三条理由**：
1. **后端有硬性接收上限，而 Codex 会毫不犹豫地超** —— 实测长会话载荷 **1.94M 字符**；
2. **网关是唯一能保证「序列稳定」的地方**（agent 自压每轮结果都不同 → 缓存失效；
   上游看不到完整请求；网关投影**结果确定** → 序列稳定 → 缓存可命中）；
3. **它压的是「旧历史」不是「上下文」**（实测 `1,940,252 → 445,875`，保 23%，
   但系统提示词和 88 个工具 schema **一律不动**）。

**历史事故（压缩层存在的真正原因）**：早期二元开关超 120k 就压到 ~6k，
671k 会话被压成 5.8k → **模型丢光历史 → agent loop 反复重跑同一命令不收敛**。

#### max_tokens 钳制

**现象**：客户端写远超模型输出上限的 `max_tokens`（给上限 64k 的 hy3 写 `999999`）
→ 上游 400 → **整条 agent 死**。

**修法 `clamp_max_tokens(body, max_output_tokens)`：能钳就钳，钳不了才报错，钳了要告知。**

| 场景 | 行为 |
|---|---|
| ≤ 上限 | 不动，无告知 |
| > 上限 | **钳到上限**，请求继续跑 |
| 恰好等于上限 | 不动（不算超限） |
| **上限未知（None/0/负数）** | **一律不动** —— 拉不到元数据不能反过来改写客户端参数 |
| 非整数（含 bool） | 跳过，交上游判 |

`MAX_TOKENS_FIELD_ORDER = ("max_tokens", "max_completion_tokens")` —— 两字段同等对待。
三端点全接，位置在 `resolve_model()` **之后**。

**实测**：hy3 + `max_tokens=999999` → **200**（钳到 64000），日志 `clamp[max_tokens 999999→64000]`。

### 2.11 【10-09】客户端用量可见 —— 看板从「只看网关」到「网关 + 客户端合计」（★新）

**现象**：看板只统计**经本网关转发**的 token（Codex / Claude Code / curl）。
WorkBuddy 桌面端**自己**调用同一批模型时不经过网关，这部分完全不可见 →

**先走死的一条路（记下免得重走）**：想从**官方接口**拿客户端用量 —— 不可行。
猜的 5 个用量明细接口（`get-user-usage-detail` / `list-user-usage` / `get-user-usage-record` /
`get-user-consume-detail` / `get-daily-usage`）**全 404**；客户端 `app.asar` 里 26 个

⇒ **教训：接口不要靠猜，去看客户端自己的落盘文件。**

**★★★★ 决定性发现：数据本来就在本机。**

```
C:\Users\Administrator\.workbuddy\traces\<workerPid>\trace_*.json
```

客户端把每次模型调用都写成了 trace。取法：
- 顶层 `trace.startedAt` → 日期/小时；**⚠ 顶层 `trace.totalTokens` 实测恒为 0，别用**；
- `spans[]` 里 **`type == "generation"`** 的才是模型调用；其 `toolOutput` 是
  **一段 JSON 字符串**（要二次 `json.loads`），解析后是标准 OpenAI 响应体，含 `model` + `usage`。

实测规模：**1221 文件 / 5868 次调用 / 8.96 亿 token / 覆盖 09-17~10-09**。

**★ 口径地基：两套账不重复，可以相加。**

| 账 | 来源 | 记什么 |
|---|---|---|
| 网关账 | `usage-stats.jsonl` | 经本网关转发的调用（Codex / Claude Code / curl） |
| 客户端账 | `~/.workbuddy/traces/**` | WorkBuddy 桌面端自己的调用 |

五字段（prompt / completion / total / cached / reasoning）同名同义，**直接相加 = 模型整体用量**。
（别再混入 8731 的 `quota.used` —— 那是 **credits** 单位、账号级容量，与 token 不是一回事。）

**修法（三处）**：

| # | 文件 | 做了什么 |
|---|---|---|
| 1 | `deploy/wb_trace_stats.py` | **新增**只读聚合器 `WbTraceIndex`：`day()` / `daily()` / `models()` / `available_days()` / `summary()`。**文件级 mtime 缓存**（首扫 6.6s → 复扫 0.06s）；任何单文件解析失败只跳过、绝不抛 |

| 3 | 计划任务 `gt-dashboard-8735` | **新增**。原 8735 靠 serve-loop 顺风车，**有缺陷**（见下） |

**★ 顺带修掉的架构缺陷**：`serve-loop.bat` 的 `:loop` 是
`探8735（down就start）→ 探8787（健康就exit）→ python -m gtwb（前台阻塞）`。
**网关一直健康时它整轮就退出，永不回循环顶部再检查 8735** ——
所以 8735 只在网关重启时被顺带拉起。已改为**独立计划任务**（照抄 8731 模式）：

## 4. 方法论沉淀（最值钱的部分）

### 4.1 影子实例调试法
改坏主干时，在 `8788` / `8789` 起**独立实例**（独立 state/log）复现 traceback。
本次靠它定位了「全部 500 且日志无痕迹」的缩进错误。
> 命令范式：`GTWB_BACKEND=... python -m gtwb --port 8799 --log _t/shadow3.log --state-file _t/state3.json --skip-check`

### 4.2 诊断日志先行
怀疑「静默丢弃」类问题时，**先让网关每请求落「声明清单 + drop 告警」**，拿实锤再动手。
不要在看不见的地方猜。

### 4.3 逐项减法定位法
面对「某个上游报错不知道谁触发」：**一次只改动一个变量**，看结果翻转点。
本次 `11128` 靠它锁定到「身份声明句」这唯一一处。

### 4.4 离线复现脚本
把「偶发」变成「确定性」。`repro_11148.py` 用同一份转换函数构造四种场景，
修复前后对照一目了然，回归断言也有了依据。

### 4.5 对标开源的取舍框架
| 场景 | 该搬什么 |
|---|---|
| 单用户单上游 | 多租户 / 计费 / 账号池 / OAuth → **一律跳过** |
| 同上 | 「可靠性」（重试、上限、透传）+「保真度」（不改写内容）→ **必搬** |

### 4.6 三条通用工程纪律（与具体实现无关，务必带走）

> **① 网关自用参数走函数入参，绝不塞进 `body`。**
> `body` 是整体 `json=body` 发上游的，多一个未知字段上游会校验失败。
> （10-09 我们第一版就把 `max_input_tokens` 写成了 body 字段，自己发现后改掉，并加断言锁死。）

> **② 先定模型，再做任何与模型能力相关的决策。**
> 投影阈值依赖模型容量，而 `resolve_model()` 会把客户端写错的模型名换成真实名。
> 顺序反了就是拿「错的模型」查容量 → 阈值失真。

> **③ 改投影/转换层之前，先跑回归。**
> 这类代码牵一发动全身，本次多次靠回归（当前 205 项）拦住回归缺陷。

## 8. 怎么同步到你那台

### 8.1 推荐路径：拉同一个 git 提交（保证字节一致）

```bash
cd <你的 gt-wb-gateway 目录>
git fetch origin
git log --oneline HEAD..origin/main        # 看远端多了什么
git merge --ff-only origin/main            # 快进；有分叉再议
./.venv/Scripts/python.exe tests/test_gateway.py   # 必须 205 全过
# 然后按 5.3 重启 + 5.1 验收
```

**⚠ 别用「复制文件夹」** —— Windows `core.autocrlf` 会在检出时把 LF 改写成 CRLF，
凡是仓库带哈希清单的项目，本地校验会通过、CI 会失败。

### 8.2 如果你的代码结构不同

那就把 **第 4 节的方法论 + 三条通用纪律**带走，核心只有四句：

1. **投影阈值要按 `该请求模型的 maxInputTokens` 动态算**，别写死字符数；
2. **`/v1/models` 要把 `context_length` 告诉下游**（OpenAI 兼容字段）；
3. **`max_tokens` 超模型输出上限时钳制并告知**，别让上游 400 打死 agent；
4. **网关自用参数走函数入参，绝不塞进 body；先定模型再做与模型能力相关的决策。**

### 8.3 排障顺序（出问题时按这个走）

```
1. curl --noproxy "*" :8787/health          → 服务活着吗？nickname 是明文吗？
2. python -m gtwb --diag                    → 谁在连？各客户端成功率？
3. 看 gtwb.log / usage-stats.jsonl 末条时间  → 到底有没有流量进来？
4. 有 rid 就 grep 那一条                    → 投影档位 + 上游错误原文
5. 需要看客户端发了什么 → GTWB_CAPTURE_DIR 后重放
```
