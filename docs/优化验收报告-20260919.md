## 二、你问的"是协议问题还是配置问题"——都不是

你原话是怀疑"协议 response 问题"或"公司电脑配置问题"。逐条查证后，两个都不是主因：

| 怀疑对象 | 查证结果 | 证据 |
|---|---|---|
| Responses 协议转换有 bug | **协议转换本身是好的**。转换后的 messages、tools、tool_call_id 对应关系全对，模型也确实按工具规范调用 | 三协议冒烟 3/3；真实抓包 `function_call_output` 与 `function_call` 的 `call_id` 一一对应 |
| 公司电脑/网络配置问题 | **不是**。请求能到达上游，只是内容被网关自己的投影层砍了 | 抓包显示上游返回 200 或 400/11128，网络从未超时 |
| Mac 的 Codex 配置问题 | **是次要问题**。`wire_api = "responses"` 本来就配对，但缺 `experimental_bearer_token`，鉴权只押在 `~/.codex/auth.json` 上，一旦缺失就 401 且报错指向"登录"，最难排查 | 见第六节实测 |

**真正的根因在网关内部**——它把一个 47KB 的合法 Codex 请求，处理成了上游要么拦、要么看不懂的东西。

## 三、根因诊断（三条，都有实证）

### 根因 1：投影层"二元开关"，一把砍掉 99% 上下文

旧实现：只要请求 >120k 字符，就整包压缩到约 6k。

用真实 Codex 抓包（`_t/cap/req_002.json`，47,053 字符）实测：

| 项目 | 原始 | 旧投影后 |
|---|---|---|
| instructions | 21,026 字符 | **173 字符** |
| 工具 description | 9 个非空 | **全部清空** |
| 仓库指令 / AGENTS.md | 有 | 丢失 |

模型拿不到操作手册，自然不按规范调工具、不收敛——**这才是"function call 不好用"的第一主因**。

### 根因 2：身份声明句触发上游安全策略（code 11128）

无损档首轮仍被上游拒：

```
{"code":11128,"msg":"Illegal API invocation from an unapproved channel"}
```

用 `_t/diag_11128.py` 做逐项减法定位，结论非常干净：

| 减法动作 | 结果 |
|---|---|
| 仅删「身份声明句」（1 处） | ✅ 200 |
| 仅删「Codex 品牌词」（13 处） | ✅ 200 |
| 删掉全部 harness 段 | ✅ 200 |
| **保留身份句、只清空工具描述** | ❌ 400 / 11128 |

→ **唯一触发点就是身份声明句**（"You are a coding agent running in the Codex CLI" 之类），
与指令正文、工具描述、提示词长度都无关。

修法不是"整段压缩"，而是**只中和身份、逐字保留行为指令**（`neutralize_identity_text`）。

### 根因 3：关键字段被静默丢弃

| 字段 | 后果 |
|---|---|
| `reasoning.effort`（嵌套结构） | 推理强度没传上去，agent 决策质量下降 |
| `prompt_cache_key` | 上游缓存失效，每轮都全量重算（也更容易被风控盯上） |
| `parallel_tool_calls` | 模型不敢并行调工具，多步任务轮数翻倍 |
| 模型名不兜底 | 客户端发 `gpt-5.6-luna` / `gpt-6-astra` 这类上游不存在的名字 → 400，**整条 agent 直接崩** |

## 六、Mac 侧配置修正（直接回答"是不是我们这边的配置问题"）

现有 Mac 接入包的 Codex 配置：

```toml
[model_providers.custom]
base_url = "http://192.168.191.81:8787/v1"
wire_api = "responses"          # ✓ 正确
requires_openai_auth = true     # ⚠ 只写这句，key 只能去 ~/.codex/auth.json 取
```

**缺 `experimental_bearer_token`**。风险很隐蔽：一旦 `auth.json` 缺失/过期（换机、
CC Switch 没写、手删过缓存），请求就 401，而 Codex 的报错会指向"登录"，
你很难联想到是接入包的问题。

已修正：

```toml
requires_openai_auth = true
experimental_bearer_token = "<api key>"   # 新增
```

实测验证：**删掉 `auth.json`、只留这个字段，真实 agent 任务照样跑通**（读 42 → 写 84，结果正确）。

同时已刷新 `deploy/home-client-kit-mac/deeplink.txt`（重新导入一次即可生效）。
注意：`deploy/home-client-kit-mac.rar` 是旧打包件，需要时请重新打包。

## 九、客户端身份上报（用量明细的「客户端」列）

### 现象
`workbuddy.cn` → 个人主页 → 套餐与用量 → 用量明细，共四列：
时间 / 积分消耗 / 模型 / **客户端**。官方客户端产生的记录，「客户端」列显示
`WorkBuddy`；经网关产生的记录，该列为空。

### 根因
不是出错，是**我们没发那组头**。后端靠请求头判断"这次调用来自哪个客户端"，
而网关早期只发了 `Authorization` 与 `X-Product: SaaS`，漏掉了 IDE 身份三件套。

证据取自本机安装包（非推测）：

1. 桌面端 `resources/app.asar` 向被拉起的 agent-cli 注入
   `CLIENT_INFO_PLATFORM` / `CLIENT_INFO_IDE_TYPE = "WorkBuddy"`、
   `CLIENT_INFO_USER_AGENT_EXTENSION = CLI/<cliVersion>`；
2. agent-cli 的组头逻辑：`X-IDE-Type = ideType || PRODUCT_TYPE`、
   `X-IDE-Name = platform || PRODUCT_TYPE`、`X-IDE-Version = platformVersion`、
   `X-Product = deploymentType`；UA 为
   `<product>/<ver> <platform>/<ver> CLI/<cliVer>`；
3. 桌面端源码注释自述该版本号"用于服务端白名单识别客户端身份"。

### 改动
`upstream.py::chat_headers()` 按官方形状补齐，取值由 `config.py` 提供：

| 头 | 改前 | 改后 |
|---|---|---|
| `X-IDE-Type` | 未发 | `WorkBuddy` |
| `X-IDE-Name` | 未发 | `WorkBuddy` |
| `X-IDE-Version` | 未发 | `5.5.6`（自动探测本机安装版本） |
| `X-Product` | `SaaS` | `SaaS`（不变，与官方聊天链路一致） |
| `User-Agent` | `CLI/2.63.2 CodeBuddy/2.63.2` | `WorkBuddy/5.5.6 WorkBuddy/5.5.6 CLI/2.137.1` |

客户端版本**自动探测**（读本机 `install-manifest.json` 的 `appVersion`），
客户端升级后无需改配置。开关 `client_identity`（默认开），
可用 `GTWB_CLIENT_IDENTITY=0` 关闭做 A/B。

### 验证
用本地回显上游接住网关实际发出的请求，确证头上线：

```
User-Agent: WorkBuddy/5.5.6 WorkBuddy/5.5.6 CLI/2.137.1
X-Product: SaaS
X-IDE-Type: WorkBuddy
X-IDE-Name: WorkBuddy
X-IDE-Version: 5.5.6
```

回归 89 → 99 项（新增 10 项身份断言）；真实 Codex agent 端到端仍为
3 轮全透明档、全 200、`escalated=0`、400 为 0。

### 边界（需要说清）
- 它让用量明细的归因**准确**，也让流量不再表现为"来源不明"。
- 它**不改变**"用第三方客户端消耗订阅额度"这一行为本身的性质——那取决于订阅条款，
  与发不发这组头无关。
- 历史记录不会追溯标记，只有改动之后产生的调用才带客户端名。
