# gt-wb-gateway 部署指南（macOS / MacBook）

> 用途：把这台 Mac 部署成**独立上游**，用自己的 WorkBuddy 订阅对外提供模型 API。
> 全部结论来自一台 Windows 上跑了一个月网关的实测记录（2026-09-11 起），
> macOS 差异已单独标注并在代码/脚本中处理。
>
> **每步验证通过再进下一步。卡住就停下报告，不要静默降级、不要猜。**

---

## 0. 先搞清定位：你是「上游」，不是「客户端」

| | Mac 当**客户端** | Mac 当**独立上游**（本文档） |
|---|---|---|
| 装 WorkBuddy 桌面端并登录 | 不装 | **必须装并登录** |
| 跑网关 | 不跑 | **跑，且开机自启** |
| 登录态用途 | — | 复用订阅，作为上游配额池 |
| 谁连它 | 它连别人 | 别的机器（Codex/Claude Code）连它 |

你要做的是右边那列。

## 1. 前置条件

| 项 | 要求 | 检查方式 |
|---|---|---|
| WorkBuddy 桌面端 | 已装、**已登录**（不要退出） | 手动打开确认 |
| Python | 3.10+（建议 3.13） | `python3 --version` |
| uv | 装 venv 用 | `uv --version`（没有：`brew install uv`） |
| 网络 | 能访问上游 | 见第 3 步 `/health` |

**登录态是自动发现的，不需要手填 token。** macOS 路径已在代码里内置
（`gtwb/auth.py` 的 `candidate_paths()`）：

```
~/Library/Application Support/CodeBuddyExtension/Data/Public/auth/*.info
```

找不到时用第 3 步的探测命令确认实际路径，再看第 8 节。

## 5. config.json 要点

```jsonc
{
  "host": "0.0.0.0",        // 监听非 127.0.0.1 时必须设 api_key，否则等于把账号借给整个网段
  "port": 8787,
  "api_key": "<自己生成的一把，与别的机器不同>",
  "backend": "https://copilot.tencent.com",
  "web_origin": "https://www.codebuddy.cn",
  "web_search": true,
  "capture_dir": null,      // 抓包开关，排障时才开，平时关（要重启才生效，且占磁盘）
  "allow_account_rotation": false
}
```

- **上游域名不通用**：换账号（如国际版站点）时先看 `/health` 的 `account.domain`，
  与基线 `www.codebuddy.cn` 不同才需要设 `GTWB_BACKEND` / `GTWB_WEB_ORINY_ORIGIN`（环境变量支持）。
- **`capture_dir` 平时必须关**：开了每个请求落盘 500KB+，长会话一天能写几十 GB。

## 6. 开机自启（macOS 用 launchd，不是计划任务）

```bash
chmod +x deploy/serve-loop.sh          # CRLF 会导致 bad interpreter，必须 LF
sed -e "s#__REPO__#$HOME/gt-wb-gateway#g" \
    -e "s#__PYTHON__#$HOME/gt-wb-gateway/.venv/bin/python#g" \
    deploy/com.gtwb.gateway.plist > ~/Library/LaunchAgents/com.gtwb.gateway.plist

launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.gtwb.gateway.plist
launchctl print gui/$(id -u)/com.gtwb.gateway | head -20
```

看门狗同时盯两个进程：网关（8787，前台跑，退出即重启）+ 看板（8735，每 60 秒复检）。

**验收自愈**：杀掉网关进程，约 15 秒内应自动回来。

```bash
lsof -nP -iTCP:8787 -sTCP:LISTEN | awk 'NR==2{print $2}' | xargs -r kill
sleep 15 && curl --noproxy "*" -s http://127.0.0.1:8787/health
```

**卸载**：`launchctl bootout gui/$(id -u)/com.gtwb.gateway`

## 7. macOS 专属差异与踩坑（Windows 上没这些）

| # | 坑 | 正解 |
|---|---|---|
| 1 | **代理劫持健康探测**：装了 Clash Verge 后 shell 导出 `HTTP_PROXY`，`urllib` 探 `127.0.0.1` 被劫到代理必失败 → 看门狗误判「网关已死」→ 反复拉起抢端口的僵尸进程 | `serve-loop.sh` 顶部已清空代理变量；**任何自己写的探测一律 `curl --noproxy "*"`** |
| 2 | **shell 脚本 CRLF** → `bad interpreter: /bin/bash^M`，看门狗静默不运行 | 保持 LF；`file deploy/serve-loop.sh` 应显示 `ASCII text` 而非 `with CRLF` |
| 3 | **Python 路径是 `.venv/bin/python`**，不是 `.venv/Scripts/python.exe` | 全部命令用 `bin/` |
| 4 | **`taskkill` / `netstat -ano` / `schtasks` 全不存在** | 用 `lsof -nP -iTCP:8787 -sTCP:LISTEN` 找 PID、`kill <pid>` 停、`launchctl` 管常驻 |
| 5 | **僵尸 codex.exe 锁死**（Windows 侧踩过；Mac 上同类现象是 codex 进程残留） | `pkill -f codex` 后重试；排查 codex 卡死先做这步 |
| 6 | **`systemd` 不存在** | 用 launchd（见第 6 节） |
| 7 | **`~/.codex/config.toml` 的 `CODEX_HOME` 要从 shell 设**，从 `.bat`/脚本里 export 可能不被采纳 | Mac 上用 `.zshrc` 或直接命令行 export |

### 与 Windows 共享的通用坑（同样适用）

| # | 现象 | 正解 |
|---|---|---|
| 8 | **上游 400 `code 11128`** | 身份声明句（"You are Codex"）是唯一触发点。网关已做 `neutralize_identity_text()`，**不要关掉** |
| 9 | **模型不按规范调工具、任务不收敛** | 投影层会压缩上下文；已是弹性档（600k 字符内透明）。别把 `TRANSPARENT_CHAR_LIMIT` 改回常量 |
| 10 | **模型清单里出现上游不认的模型** | 清单只取「主 CLI agent」那一层；`model_guard` 默认开，别关 |
| 11 | **用量明细「客户端」列为空** | 网关已发 `X-IDE-Type/Name/Version` 三件套 |
| 12 | **模型 429 限流** | 见下节，**不是故障** |

## 8. 排障入口

```bash
# 一键诊断：谁在连 / 成功率 / 最近异常
.venv/bin/python -m gtwb --diag [--lines 40]

# 生效配置
.venv/bin/python -m gtwb --show-config

# 实时看板
open http://127.0.0.1:8735        # 三板块：总览 / 模型用量 / 按日明细
```

**登录态找不到时**（不发请求，纯本地）：

```bash
find ~/Library/Application\ Support -name "*.info" 2>/dev/null
# 若路径不同，用 --auth-file 指定，或把目录塞进 GTWB_AUTH_FILE 环境变量
```

**多机排查固定顺序**：
① `--diag` 看该客户端有没有记录（一条都没有 = 根本没连上，查网络/鉴权/地址）
→ ② 有失败拿 `rid` 去 `gtwb.log` grep，看投影档位与上游错误原文
→ ③ 还要看客户端发了什么 → 临时开 `capture_dir` 重启，让它重放一次，查完关掉
→ ④ 降级重试持续集中在**某一个**客户端 = 该客户端 system prompt 触发风控

---

## 9. 上游 429 限流：不是故障，别慌（2026-10-13 实测）

上游对**每个模型单独**计频率窗口，超了返回 `code 6004`，**报错正文里直接写着重置时刻**：

```
{"code":6004,"msg":"您的使用量已超出频率限制，将在 2026-10-13 12:09:24 UTC+8 重置，
 您也可以切换其他模型继续使用。"}
```

实测特征：
- **配额没打光**（`/v2/billing/meter/get-user-resource` 显示仍有余额）时也会 429，纯粹是速率；
- **不同模型重置时间不同**（step-5 是 12:09、hy4 是 23:00）⇒ 分模型计窗口，可切换模型继续；
- 上游**不返回 `Retry-After` 头**，重置时间只在 body 里；
- 实测触发量级：单会话上下文 14~29 万 token、每 5 秒一轮，连跑几百轮即触发。

⚠ **排查陷阱**：网关的熔断是**账号级**的，任一模型 429 会让**所有**模型一起进冷却
（`60s × 2^n`，最长 2 小时），期间别的模型返回 `503 account unavailable: cooldown Ns`。
**这不是上游在限流它**，是本地熔断挡在门口。等冷却过去单测才能判断。
所以：**换模型继续干活，别在同一个模型上反复重试**——每次失败都让退避翻倍。

## 11. 红线（务必遵守）

1. **灰区用法**：复用订阅登录态转第三方客户端属条款灰区（官方条款有上报机制）。
   默认单账号、低频、`allow_account_rotation=false`。
2. **同账号不跨机登录**：绝不要让另一台机器登你这个账号，也**严禁互拷 `*.info` 登录态文件**
   ——那等于把两个账号合成一个，直接踩风控红线（账号被封）。
3. **多机要用就多账号**：两台各登各的账号、各自独立部署，才是最安全的形态。
4. **监听非 127.0.0.1 必须设 api_key**，防火墙只放行需要的网段，绝不开公网。
5. **敏感文件不外发**：`config.json` / `state.json`（含 uid）/ `*.info`（明文令牌）都不入库、不外发。
6. **`state.json` / `*.info` 严禁跨机互拷**。
